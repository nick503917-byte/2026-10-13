# OA串接SAPB1｜規劃、介面與登入問題

整理日期：2026-10-13。

## 1. 目標與目前進度

目標是讓泛微 OA 的資料依指定流程傳入 SAP Business One，並把處理結果回覆 OA。工作方向是本機 Visual Studio 開發，完成後部署到 SAP B1 Windows 主機。

目前找到三類來源：OA 專案的溝通規劃、卡控專案中的 Service Layer 登入測試、後來獨立的 OA 學習聊天。已有規劃與測試討論，但沒有完整 OA 表單成功建立 SAP 單據並回寫的證據。

2026-09-24 的新聊天先約定循序漸進，當時不建立專案、不安裝環境、不連正式系統。這是該次新任務的起點，不代表更早的登入測試不存在。

## 2. 系統分工草案

| 系統 | 擬負責的範圍 |
|---|---|
| 泛微 OA | 填單、簽核、附件、流程狀態與通知 |
| 中介服務 | 欄位及代碼轉換、驗證、佇列、防重、重試、日誌 |
| SAP B1 | 主資料檢核、單據編號、正式單據、庫存及帳務 |

```text
OA 申請／簽核
    → 中介接收與驗證
    → SAP API 建立草稿或正式單據
    → 保存 DocEntry、DocNum、物件類型與結果
    → 回覆 OA／查詢後續狀態
```

以上是目前規劃，還不是雙方已確認的介面契約。OA 直接呼叫或經中介、草稿或正式單據、SAP 是否再跑審批程序，都需要明確決定。

## 3. 第一次介接會議需要確認的內容

| 面向 | 要取得的答案 |
|---|---|
| 泛微環境 | 確切產品、版本、部署方式、API 文件及模組授權 |
| SAP 環境 | 公司別、SAP 版本／修補層級、SQL Server 或 HANA、Service Layer 可用性 |
| 第一個流程 | 例如採購申請或採購訂單；何時觸發、誰核准、誰負責 |
| 寫入階段 | 草稿、正式單據或自訂資料；OA 核准與 SAP 簽核如何協作 |
| 反向流程 | 撤回、退回、取消、修改、SAP 後續狀態如何回 OA |
| 附件 | 保存位置、傳檔方式、權限與失敗處理 |
| 成功定義 | 回傳單號就完成，或還要核對內容、簽核及後續狀態 |

先確認流程與責任，再訂欄位 mapping。尚未看到正式核定的第一張表單與最終欄位清單。

## 4. 技術名詞與選型紀錄

| 技術 | 目前在本專案的角色 |
|---|---|
| Service Layer | HTTP／OData／JSON 介面；曾測試登入，後續跨系統串接候選方案 |
| DI API | Windows COM 業務物件介面；Add-on 練習已使用，可作其他整合候選 |
| UI API | SAP Client 畫面與事件；不是 OA 背景整合必須依附的架構 |
| B1if | 歷史規劃列為整合框架候選，未見實作紀錄 |

歷史討論的路徑對應為 `/b1s/v1` 與 `/b1s/v2`；實際採用哪個版本，需要由目標環境支援及正式 API 文件確認。這份筆記沒有替目前伺服器驗證 API 清單。

標準交易應以核定的 SAP API 處理；不把 OA 直接 INSERT／UPDATE SAP 標準交易表納入本方案。

## 5. Service Layer 登入診斷紀錄

來源聊天：「查找 SAPB1 串接方法」（原屬卡控專案）。

歷史聊天記載：

- 50000 連接埠可連線，C# 可以送出 Login 請求。
- 多個可登入 SAP 桌面版的帳號，在 Service Layer 收到錯誤碼 206，訊息 Invalid login credential。
- Controller 的 Settings／Monitor 畫面空白。
- Apache 日誌出現 balancer-manager cross-site access 訊息。
- 搜尋指定名稱的登入日誌沒有找到結果。

**目前結論：登入問題未結案。** 當時回答曾直接斷言是伺服器配置，但已知線索還不足以排除帳號映射、公司名稱、驗證模式、權限及版本等原因；本筆記將其收斂為待查項目，不沿用過度確定的根因判斷。

### 下一輪應留下的證據

1. 指定伺服器及連接埠是否有正確服務監聽。
2. Service Layer、Server Tools、公司資料庫與 SBO-COMMON 的版本。
3. SLD 中的資料庫執行個體及公司映射。
4. 登入請求的公司名稱、帳號種類及遮罩後錯誤回覆。
5. Controller 使用相同主機名稱時的行為與瀏覽器錯誤。
6. 與單次重現時間吻合的服務端日誌。

未找到日誌不等於沒有產生日誌，可能是位置、名稱、權限或設定不同。連接埠通也不代表登入與業務 API 可用。先完成登入，再測一個唯讀查詢，再進入建單。

## 6. 欄位對應表應包含什麼

下表是整理後的規格模板，不是既有實作欄位名。

| 項目 | 需要記錄 |
|---|---|
| 來源識別 | OA 系統、表單 ID、版本、操作類型、Request ID |
| 目標公司 | SAP 公司別及允許操作的物件 |
| 單頭 | 客戶／供應商、日期、幣別、倉庫或其他共同欄位 |
| 明細 | 料號／科目、數量、單位、稅碼、價格、成本中心等 |
| 代碼對照 | OA 代碼、SAP 代碼、維護人、缺少對照的處理方式 |
| 回覆 | 狀態、Object Type、DocEntry、DocNum、可讀錯誤訊息 |
| 附件與追蹤 | 附件識別、OA 原單號 UDF、時間與操作紀錄 |

日期、精度、必填、最大長度、NULL、預設值與修改規則，也要逐欄定義。

## 7. 防重、重試與例外設計

### 防重

相同 OA 請求逾時後可能已在 SAP 成功，不能盲目再建單。先前討論有用來源系統＋OARequestId＋Operation 當固定識別的方向，SAP UDF 保存來源編號。

整理補充：只有「查一次是否存在」不足以抵擋同時重送。規格還要定義併發控制、唯一性保證、處理中狀態及查回結果；這些目前尚未實作。

### 錯誤分類

| 類別 | 建議的處理方向（待定案） |
|---|---|
| 業務資料錯誤 | 提示欄位／規則，修正後重送 |
| 權限或認證錯誤 | 交由維運處理，不持續無限重試 |
| 暫時網路／服務錯誤 | 有上限、間隔與日誌的重試 |
| 成功與否不確定 | 先依固定識別查回 SAP 結果 |
| 多張單據部分成功 | 定義接續、取消、補償或人工處理 |

必要日誌：來源單号、公司、操作、請求識別、時間、重試次數、狀態、SAP 錯誤碼與目標單號；不記錄帳密或完整 Session。

## 8. 分階段驗收建議

- [ ] 登入：有效與無效帳號、指定公司、Session 到期。
- [ ] 唯讀：一筆已知主檔可查得，欄位與 SAP 畫面一致。
- [ ] 單筆建單：先選定唯一流程，核對單頭、明細、UDF 與回覆。
- [ ] 防重：同一請求連續及同時送出，不產生多張正式單據。
- [ ] 逾時：SAP 成功但 OA 未收到回覆時，可查回原單。
- [ ] 撤回與取消：依已核定規則處理，不只改 OA 畫面狀態。
- [ ] 異常與恢復：停機、重啟、權限不足、部分成功都有可追查結果。
- [ ] 上線：監控、回補、帳號權限、維護責任及版本回復。
