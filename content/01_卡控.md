# 卡控｜SAP B1 交易規則與問題紀錄

整理日期：2026-10-13。來源專案名稱：維熹卡控。

## 1. 專案用途與狀態

主要工作是以 `SBO_SP_TransactionNotification` 檢查單據、草稿與主檔的必填及業務條件，另外累積了欄位回填、過帳後處理和查詢問題。現有 SQL 多為討論後產出的版本，未找到全部規則已部署並驗收的紀錄。

## 2. 程序與資料定位

| 項目 | 在本專案中的用途／注意事項 |
|---|---|
| TransactionNotification | 交易提交前的檢核入口；用 error 與 error_message 阻擋不符條件的交易 |
| PostTransactionNotice | 交易提交後的通知；不能把它當成阻擋原交易的入口 |
| A／U | 新增／更新；各規則需確認是否兩者都檢查 |
| Object Type | 判斷物件種類，例如 17 銷售訂單、20 收貨採購、112 草稿 |
| Series | 單據系列；不可與 Object Type 混為一談 |
| DocEntry | 單據內部鍵；不要直接等同顯示單號 DocNum |
| 草稿 | 使用 ODRF／DRF1，還要以 ODRF.ObjType 判斷實際單據類型 |
| 主資料型 UDO | 要確認以 Code 或其他鍵識別，不可一律套用 DocEntry |

一般定位流程：判斷物件與動作 → 限定本次主鍵 → 取得單頭／單身 → 檢查規則 → 回傳錯誤。舊程序曾因缺少本次 ItemCode 條件，將群組 103 全部品項名稱重算，這是本專案重要的範圍控制教訓。

## 3. 最新銷售訂單規則（2026-10-06）

來源：聊天「修正銷售型態6與客戶檢核」、ORDR_總公司銷售型態卡控.sql、ORDR_最終客戶與必填卡控.sql。

適用：正式銷售訂單與銷售訂單草稿，新增及更新。

| 錯誤碼 | 阻擋條件 | 備註 |
|---|---|---|
| 10001 | CardCode=S99551 與 U_SALETYPE=6 僅一項成立 | 是雙向配對，不只限制型態 6 的客戶 |
| 10002 | 銷售型態非 6，且 CardCode 與 U_CUSCODE 不同 | 最終客戶應與客戶相同 |
| 10003 | U_SALETYPE 為 NULL、空字串或全空白 | 必填 |
| 10004 | U_CUSCODE 為 NULL、空字串或全空白 | 必填 |
| 10005 | 任一明細 FINALPRICETEST 為 NULL 或 0 | 數字欄位，最新需求明確禁止 0 |

10001 的四種基本案例：

| 客戶為 S99551 | 型態為 6 | 10001 結果 |
|---|---|---|
| 是 | 是 | 不阻擋 |
| 是 | 否 | 阻擋 |
| 否 | 是 | 阻擋 |
| 否 | 否 | 不阻擋；仍需接受其他規則檢查 |

目前第二個 SQL 檔會保留已有錯誤，內部先檢查 10003、10004、10005，最後才檢查 10002。整份主程序中後面的其他區段是否覆蓋錯誤，仍需一起檢視。

### 必須保留的版本差異

2026-09-08「新增銷售型態必填欄位」使用 `U_FINALPRICETEST`，且只有 `DocType='I'` 檢查明細；表頭也包含 `U_SALEPRICE`。2026-10-06 新檔使用使用者指定的 `FINALPRICETEST`，未加 DocType 限制，也未納入 U_SALEPRICE。

不能自行認定新檔已取代所有舊需求。需核對：實際欄位是否有 U_ 前綴、RDR1 與 DRF1 是否皆存在、服務型單據是否排除、U_SALEPRICE 是否仍必填。

狀態：已產出 SQL；最新聊天明確記載尚未套用資料庫或實機驗證。

## 4. 系列與 UDO 對照

核心對應為：`[@FORM_NUM].U_SystemCode` 對單據 `Series`，`U_CategoryName` 對 `U_TypeName`。Object Type 只用於判斷本次單據類型。

| 版本／情境 | 內容 |
|---|---|
| 收貨採購 Series=11 | 正式 OPDN 與 ODRF.ObjType=20 草稿，依系列檢查類別名稱；草案錯誤碼 -5001／-5002 |
| 2026-08-18 擴充版 | 同時比對 Series、U_TypeName、U_ChangeType、U_ChangeReason；涵蓋多種單據及草稿，生產收發貨另限制 BaseType=202 |
| 2026-09-04 簡化版 | 對採購單、AR 發票、銷售訂單及其草稿，只比對 Series＋U_TypeName，錯誤碼 2008 |

三者的範圍不同，不能直接全部疊加。簡化版不代表所有單據都已取消異動區分／原因檢核，需由需求負責人確認。

## 5. 退貨與調撥

### 退貨原因

- `return_reason_validation_clean.sql` 整理了重複的舊版與 Nick V1，保留較完整的版本設計，含服務型文件處理。
- 已指出舊 SQL 的採購退貨表身誤用 PDN1，應核對 RPD1。
- 草稿退貨必填檢查使用 2203，正式單據版本使用 2204。
- 另一份 `RRR1_RDN1_退貨原因卡控.sql` 限制銷售退貨請求與銷售退貨的 `U_ReturnReason`，禁止 RR11～RR16，錯誤碼 1601。
- 這份禁止原因的獨立檔只有正式單據區塊；不能推定草稿也已加入相同限制。

早期總覽曾將銷售退貨請求寫成 231000000，但較後 SQL 使用 234000031，需以目標環境物件定義核對；不要照抄舊總覽的編號。

### 庫存調撥參考文件

聊天「新增庫存調撥參考文件卡控」要求正式單據與草稿都檢查參考文件。討論版本使用 OWTR／WTR21、ODRF／DRF21；測試系列 21，正式需求系列 111。系統參考文件與外部參考文件採不同有效值條件。尚無完整實測通過紀錄。

## 6. 其他規則與錯誤教訓

| 主題 | 已整理的重點 |
|---|---|
| UDO 特殊字元 | RAWITEMCREA1 的 U_ItemCode 限制中文、英文字母、數字；先確認 OUDO.Code 與表身實際主鍵，最後討論改以 Code 定位 |
| EXA2 轉 int 失敗 | 曾懷疑 TransactionNotification 混用數字與文字 Object Type 造成隱含轉型；保留為排查方向，不宣稱根因已完成驗證 |
| AP 貸項卡控不執行 | 歷史 SQL 將 Object Type=19 區塊包在 Object Type=59 內，兩條件無法同時成立，需分開區塊 |
| 生產訂單對銷售訂單 | 優先辨識 OriginAbs／DocEntry；只用 DocNum 或 ItemCode 加總可能丟失系列及明細列差異 |
| 品項必填 | 舊總覽含固定資產欄位及 24 個非資產品項欄位；詳細清單保留在來源文件，非本次重新驗證的上線清單 |
| 交貨卡控 | 舊總覽包含信用額度、批次來源訂單、付款條件 T000、運送條件等規則 |
| 錯誤覆蓋 | 舊程序可能在同一交易重設 error；交貨 1502／1504 也有重複目的的檢查 |
| 空值判斷 | `IS NOT NULL OR <> ''` 不能當成「非空白」的可靠判斷，需依欄位型態處理 |

## 7. 回填與過帳後處理（保留為歷史實作）

目前有 OITM.U_InvOwner 回填檔：外購原料取採購員姓名，自製原料取工單建立者，成品取銷售員姓名，並有群組 103／101 等條件。

也有發票號碼、OINV.JrnlMemo／OJDT.Memo 組成，以及 AR 發票日期帶來源交貨日期的討論。其中 AR 日期需求最後轉為 FMS；較早 PostTransaction SQL 不應當成最後採用方案。

這些檔案含直接 UPDATE 系統表的歷史做法。筆記只記錄其用途，沒有將它們當成本次推薦的部署方案；後續修改應先審核 SAP 支援方式與交易一致性。
