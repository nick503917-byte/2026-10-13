### 1. 如果 我生產工單開錯了 原本要開A成品 開成B成品 但我兩個零部件都是一樣的 且我的B成品已經生產收貨進來了 那我可以存貨交易 把B發出去 A收進來嗎

來源：[S110-Q001](<../../原始問答/S110_確認成品工單錯誤調帳.md#q1>)；2026-08-24

**問題**

如果 我生產工單開錯了 原本要開A成品 開成B成品 但我兩個零部件都是一樣的 且我的B成品已經生產收貨進來了 

那我可以存貨交易 把B發出去 A收進來嗎

**歷史回答**

可以做「B 發出、A 收進」的存貨重分類，但不建議直接用一般存貨交易處理，除非公司制度允許，且 A、B 的成本、批號／序號、品質規格及會計科目完全相容。

較正確的處理方式通常是：

1. 沖銷 B 成品的生產收貨。
2. 撤銷或關閉開錯的 B 生產工單。
3. 建立正確的 A 生產工單。
4. 依 A 工單重新發料並生產收貨。

這樣工單、物料耗用、成本與生產履歷才會一致。

如果 B 已經不能沖銷，才考慮做「B 轉 A」：

- B 成品做存貨發出。
- A 成品做存貨收貨。
- 數量與總成本應一致，避免憑空產生損益。
- 備註原 B 工單號、原因與核准紀錄。
- 同步處理批號／序號、效期、檢驗狀態及標籤。
- 若系統支援，使用「重分類／轉換／重工工單」會比兩張一般存貨單更合適。

即使兩個成品的零部件相同，也要確認 BOM 用量、人工與製造費、成本計算方式、單位、產品規格都相同；否則直接換料號會讓成本與生產追溯失真。若 B 已出貨、已關帳或涉及法規追溯，更不應直接轉。

簡單判斷：**尚未關帳且能沖銷，就沖銷重做；不能沖銷，經財務與品保核准後再做 B→A 重分類。**

### 2. 直接發B 收A A是正確的成品料號 發 借 過度科目 貸 製成品 收 借 製成品 貸 過渡科目

來源：[S110-Q002](<../../原始問答/S110_確認成品工單錯誤調帳.md#q2>)；2026-08-24

**問題**

直接發B 收A 

A是正確的成品料號 

發
借 過度科目
貸 製成品

收 
借 製成品
貸 過渡科目

**歷史回答**

可以，這種作法本質上是把 **B 成品重分類成 A 成品**，你的分錄方向正確：

存貨發出 B：

- 借：存貨轉換過渡科目
- 貸：製成品—B

存貨收貨 A：

- 借：製成品—A
- 貸：存貨轉換過渡科目

但要注意：

- A 的收貨總成本應等於 B 的發出總成本，讓過渡科目餘額歸零。
- 若 A、B 的系統單位成本不同，不要直接用 A 原本的標準／移動平均成本而造成差額；差額需依公司制度進成本差異科目。
- 兩張交易應交叉註明單號、原生產工單及「工單成品料號開錯」。
- 數量、倉庫、批號／序號及庫存狀態要正確承接。
- 此作法只修正庫存與會計，原生產工單仍會顯示生產 B；若需要完整生產追溯，仍以沖銷 B 生產收貨、改由 A 工單收貨最乾淨。

若只是料號開錯、實物確實符合 A 規格，而且財務與品保同意，直接發 B、收 A 是可行的。关键是**同金額轉入，過渡科目最終為零**。

### 4. 不甘上面的事情

來源：[S110-Q004](<../../原始問答/S110_確認成品工單錯誤調帳.md#q4>)；2026-08-24

**問題**

不甘上面的事情

**歷史回答**

了解，單純說 SAP Business One 原廠的「日記帳憑證（Journal Voucher）」。

它的定位是：**尚未正式過帳的日記帳分錄草稿／暫存區**。

常見使用情境包括：

- 會計人員先建立分錄，再交主管檢查與核准。
- 月底結帳時先彙整調整分錄，確認後一次正式過帳。
- 新進人員先製作憑證，由資深人員複核。
- 從其他系統匯入分錄後，先檢查再過帳。
- 分錄資料尚未完整，先暫存，之後可以修改或刪除。
- 將多筆相關分錄集中在同一張日記帳憑證內管理。

它和「日記帳分錄（Journal Entry）」的主要差異是：

| 項目 | 日記帳憑證 | 日記帳分錄 |
|---|---|---|
| 性質 | 草稿、暫存 | 正式會計交易 |
| 是否更新總帳 | 尚未正式更新 | 立即更新 |
| 能否修改或刪除 | 正式過帳前可以 | 過帳後通常只能沖銷 |
| 後續動作 | 審核後執行過帳 | 已完成過帳 |

日記帳憑證經確認並執行 **Post Voucher／過帳憑證** 後，才會轉成正式日記帳分錄；狀態也會由 Open 變成 Closed。SAP 原廠將它定義為「暫時存放尚不能正式過帳之日記帳分錄的功能」。[SAP Help：Journal Vouchers](https://help.sap.com/docs/SAP_BUSINESS_ONE/68a2e87fb29941b5bf959a184d9c6727/4510c8e00b9941dfe10000000a1553f6.html?version=9.3)、[SAP Help：Posting Journal Vouchers](https://help.sap.com/docs/PRODUCT_ID/68a2e87fb29941b5bf959a184d9c6727/45114a5429fc4805e10000000a1553f6.html?locale=en-US&state=PRODUCTION&version=9.3)

簡單講：**日記帳憑證不是另一種正式傳票，而是正式日記帳分錄的待審草稿。**

建議卡控時注意兩件事：

1. **比較完整成本，避免只比這兩欄。**  
   如果有資源成本、額外成本或副產品，應採用 SAP 的總計差異口徑：  
   `差異＝（實際產品成本＋副產品實際成本）－（實際項目元件成本＋實際資源元件成本＋實際額外成本）`  
   如果其他項目都是零，才等同於你說的兩欄相減。[SAP 成本公式](https://help.sap.com/doc/10311afc90c643b3aaceeaa87a52bf5f/10.0/en-US/How_to_Work_with_Resources_and_Production_in_SAP_Business_One.pdf)

2. **必須檢查「結單調整前」的差異。**  
   SAP 結單時可能調整產品成本、清除差異；標準成本法則可能保留差異。因此開發時要確認取值與觸發時點，不能直接拿結單調整後的零差異判斷，否則可能漏擋。[SAP 生產成本處理](https://help.sap.com/docs/PRODUCT_ID/68a2e87fb29941b5bf959a184d9c6727/689975f9caea438ba98206fce1573bcb.html)

可以交給顧問的需求是：

> 生產工單轉為「已結」時，檢核結單調整前的成本差異。若差異絕對值超過允許誤差，禁止結單，顯示「生產成本差異 XXX VND，請確認發料、退料及完工入庫後再結單」。若要求完全一致，允許誤差設為 0。

**你們用的是 SQL Server 還是 SAP HANA？產品採移動平均、FIFO，還是標準成本？** 這會影響後續卡控程式的寫法與差異判斷。

### 6. SQL Server

來源：[S188-Q002](<../../原始問答/S188_確認成本差異與工單結案卡控.md#q2>)；2026-09-18

**問題**

SQL Server

**歷史回答**

了解，你們是 **SQL Server，可以用 `SBO_SP_TransactionNotification` 做結單卡控**。

預計邏輯如下：

```text
當生產工單要轉成「已結」
→ 計算結單調整前的成本差異
→ 差異絕對值超過允許值
→ 回傳錯誤，阻止結單
```

還需要確認：**你們成品的存貨評價方法是「移動平均」、「FIFO」還是「標準成本」？** 可以在「項目主檔 → 存貨資料」查看。

這會影響差異的處理方式，確認後才能訂出正確的 SQL 檢核，避免把正常差異也擋住。

### 7. 都是移動平均

來源：[S188-Q003](<../../原始問答/S188_確認成本差異與工單結案卡控.md#q3>)；2026-09-18

**問題**

都是移動平均

**歷史回答**

那就可以把需求定為：**移動平均成品的生產工單，在結單前成本差異不為 0 時，禁止轉成「已結」。**

交給 SAP 顧問／工程師的規格可以這樣寫：

| 項目 | 卡控規則 |
|---|---|
| 系統 | SAP Business One／SQL Server |
| 實作位置 | `SBO_SP_TransactionNotification` |
| 適用時機 | 生產工單轉為「已結」時 |
| 比較金額 | 產品成本＋副產品成本－項目元件成本－資源成本－額外成本 |
| 阻擋條件 | 結單調整前的差異絕對值大於允許誤差；要求完全相等就設為 0 |
| 錯誤訊息 | 「生產成本差異為 XXX VND，不允許結單，請確認發料、退料及完工入庫。」 |

**移動平均要特別注意：有差異不一定代表資料錯誤。** SAP 原本就可能在結單時把差異調整到產品成本。設成「有差異一律擋」，等於要求使用者先處理或確認差異，才准結單。[SAP 生產成本說明](https://help.sap.com/docs/PRODUCT_ID/68a2e87fb29941b5bf959a184d9c6727/689975f9caea438ba98206fce1573bcb.html)

實作時有兩個關鍵：

- 生產工單物件為 `202`；`OWOR.Status` 的已結代碼是 **`L`**，`C` 是取消。[SAP 欄位定義](https://help.sap.com/doc/089315d8d0f8475a9fc84fb919b501a3/10.0/en-US/SDKhelp/OWOR.html)
- 要從相關成本交易核算**結單調整前**的差異，並在你們版本測試觸發時點；不能直接拿結單後已被沖平的數字判斷。

如果你們沒有資源、額外成本及副產品，這項規則就能簡化為你最初要的：**「實際項目元件成本 ≠ 實際產品成本 → 不准結單」。**

### 8. 有資源

來源：[S188-Q004](<../../原始問答/S188_確認成本差異與工單結案卡控.md#q4>)；2026-09-18

**問題**

有資源

**歷史回答**

有資源的話，**必須把「實際資源元件成本」一起計入**，不能只比較材料成本與產品成本。

如果沒有額外成本及副產品，卡控條件就是：

```text
差異＝實際產品成本
    －（實際項目元件成本＋實際資源元件成本）

差異絕對值 > 允許誤差 → 禁止轉為「已結」
```

例如：

| 項目 | 金額（VND） |
|---|---:|
| 實際項目元件成本 | 100,000 |
| 實際資源元件成本 | 20,000 |
| 實際產品成本 | 120,000 |
| 差異 | 0 → 允許結單 |

若產品成本只有 **100,000**，差異就是 **−20,000**，應阻擋結單。

**建議程式直接採完整公式**，之後出現額外成本或副產品也能正確判斷：

```text
差異＝（實際產品成本＋副產品實際成本）
    －（實際項目元件成本＋實際資源元件成本＋實際額外成本）
```

這符合 [SAP 的總計差異定義](https://help.sap.com/doc/10311afc90c643b3aaceeaa87a52bf5f/10.0/en-US/How_to_Work_with_Resources_and_Production_in_SAP_Business_One.pdf)。SQL Server 的卡控仍要檢核**結單調整前的差異**，並以實際已發出的資源成本計算，不能拿 BOM 預計資源成本代替。

### 9. 對

來源：[S188-Q005](<../../原始問答/S188_確認成本差異與工單結案卡控.md#q5>)；2026-09-18

**問題**

對

**歷史回答**

那就確定採用這個規則：

> **生產工單轉「已結」時，若結單調整前的「產品成本＋副產品成本」不等於「材料成本＋資源成本＋額外成本」，就阻止結單並顯示差異金額。**

SQL Server 會透過 `SBO_SP_TransactionNotification` 實作，允許誤差先按 **0** 設計。

要接著寫成可用的 SQL，請提供你們的 **SAP Business One 版本（含 FP／PL）**，以及現有的 **`SBO_SP_TransactionNotification` 程式內容**。需要確認成本資料來源與既有卡控，才能正確整合，避免結單自動調整後差異歸零而漏擋。

### 15. 先寫個範例給我 後續我在自己新增

來源：[S188-Q011](<../../原始問答/S188_確認成本差異與工單結案卡控.md#q11>)；2026-09-21

**問題**

先寫個範例給我 後續我在自己新增

**歷史回答**

可以。把原本測試版這一段：

```sql
ELSE IF ABS(@WS_PC_Diff) > @WS_PC_Tolerance
```

**改成下面這段**，後面的 `BEGIN ... END` 錯誤訊息保留：

```sql
ELSE IF ABS(@WS_PC_Diff) > @WS_PC_Tolerance
    AND NOT EXISTS (
        SELECT 1
        FROM dbo.OWOR W
        INNER JOIN dbo.OUSR U
            ON U.USERID = W.UserSign2
        WHERE W.DocEntry = @WS_PC_Entry
          AND U.USER_CODE IN (
              N'USER_A',   -- 換成允許放行的 SAP 登入帳號
              N'USER_B'    -- 換成允許放行的 SAP 登入帳號
          )
    )
```

之後要增加人員，只要在名單加上逗號與帳號：

```sql
AND U.USER_CODE IN (
    N'USER_A',
    N'USER_B',
    N'USER_C'
)
```

不知道帳號代碼時，可以在 SSMS 執行：

```sql
SELECT USERID, USER_CODE AS [登入帳號], U_NAME AS [使用者名稱]
FROM dbo.OUSR
ORDER BY USER_CODE;
```

**名單內的人可略過成本差異阻擋；其他既有卡控仍有效。** 找不到使用者時也不會自動放行。

這裡採用 `OWOR.UserSign2`「更新使用者」欄位。[SAP 欄位定義](https://help.sap.com/doc/089315d8d0f8475a9fc84fb919b501a3/10.0/en-US/SDKhelp/OWOR.html) 測試時請讓名單內、外兩個帳號交替操作，確認結單當下此欄位確實代表本次操作者，避免誤用前一次更新的人員。
