## 2. SQL Server Agent 與漏備份

來源：「診斷 SQL Server Agent 備份排程」。使用者描述 Agent 會停止，導致未備份。當時截圖的文字判讀是預設執行個體 MSSQLSERVER，服務名稱 SQLSERVERAGENT，Running／Manual。

已討論措施：改自動啟動、服務失敗後一分鐘重啟、另由 Windows 工作排程器定期檢查。尚未取得所有設定完成的明確證據。

要分開判讀三件事：

1. 服務是否在執行。
2. 預定備份是否真的成功完成。
3. 檔案能否還原。

關閉 SSMS 不等於關閉 Agent；Agent 重新啟動也不能直接推定漏掉的備份已自動補跑。Manual 是一個可改善的設定，不是停止原因已確定的證據。

## 3. S3 自動上傳：最後採用方向

### 最後決策

- 使用 AWS CLI 的 `s3 sync` 比對並補傳 .bak。
- 本機來源為 `D:\每日備份`，保留資料庫子資料夾結構。
- 目的為既有 S3 的「每日備份」前綴。
- AWS profile 為 `sqlbackup`。
- 腳本為 `C:\SQLUpload\Upload-DailyBackup.ps1`。
- 日誌為 `C:\SQLUpload\upload-yyyy-MM-dd.log`。
- 排程名稱為 `SQL Daily Backup to S3`，最後確認時間是每天 **00:00**。這是當時伺服器排程畫面時間；若伺服器時區不同，需核對與台北時間的對應。
- **不加 --delete，不刪除 S3 舊檔**。早期曾詢問同步刪除，後來使用者明確改為先不刪。

### 執行與驗證紀錄

| 項目 | 證據／狀態 |
|---|---|
| .ps1 正確保存 | 當時聊天確認不再只是 .log 或 .ps1.txt |
| 手動執行 | 當時回覆確認 ExitCode=0 |
| 排程存在 | 當時看到工作已儲存，狀態 Running |
| 排程最後完成 | 最後仍要求確認 END ExitCode=0；不能標示已完成驗收 |
| 重試 | 建議每 30 分鐘、最多 3 次；是否完成設定待核對 |
| 避免重疊 | 建議已執行時不啟動新執行個體；待核對 |
| 遠端與還原 | 未取得抽查與還原測試結果 |

手動成功與排程成功不同。排程帳號必須能讀來源、執行 CLI 並取得對應 profile；原討論使用手動測試成功的 Windows 帳號。

### 腳本限制

最後的簡化 sync 腳本沒有檢查 SQL 備份是否仍在寫入。00:00 只能在備份已完成的前提下使用，不能靠檔名時間證明完成。後續宜補上備份完成訊號或可驗證的交接流程。

ExitCode=0 代表該次指令成功，不能單獨證明當天每個資料庫都有新備份，也不能證明 .bak 可還原。

## 4. Cyberduck CLI 歷史問題

原先嘗試 duck CLI，但遇到 .NET 元件載入／版本不符。當時記錄為程式要求的元件版本與隨附 DLL 不一致，修復後仍有問題，曾嘗試更換 CLI 版本，最後改採 AWS CLI。

這段保留為故障經驗：程式尚未啟動成功，就不能把錯誤解釋成 S3 帳密或 Bucket 問題。這次筆記不要求重裝任何軟體，也不將舊 duck 方案和最終 AWS 腳本合併。

## 5. SAP 啟動／登入卡頓（2026-09-16）

來源：「檢查電腦健康狀況」。當時觀察：CPU 約 7～10%、磁碟約 0～1%，RAM 可用約 4.7 GB；Windows 多次記錄 SAP Business One 無回應。

進一步日誌出現公司登入失敗、介面初始化失敗與授權檢查相關訊息。其中一筆明確為：

> 訊息 60070-25：已從其他兩個站台連線，需先從其中一個站台登出。

處理方向是先從其他 SAP 工作階段登出，或由管理員核對殘留連線，再開單一 SAP 視窗測試。此訊息能解釋其中一次登入阻擋；其他已進入主功能表後才卡住的情境仍不能歸為同一原因。

歷史旁支還有 Browser Access Maximum Processes=200 的畫面討論。程序容量和單一帳號登入限制不是同一件事，不能據此認定帳號可以登入 200 次。

## 6. 記憶體升級紀錄（2026-10-07～10-08）

來源：「檢查電腦記憶體是否不足」。

| 項目 | 升級前觀察 | 升級後觀察 |
|---|---|---|
| 安裝容量 | 16 GB | 32 GB，ADATA 16 GB＋Kingston 16 GB |
| RAM 使用率 | 約 86～87% | 一次約 35%，另一次約 45～46% |
| 可用 RAM | 約 1.86～1.97 GB | 約 20 GB，另一次約 16.5～16.8 GB |
| 已認可記憶體 | 約 25.25～25.62／27.17 GB | 後續約 20／43.7 GB |

設備記錄：ThinkPad T14 Gen 5／21MDS3DE00、AMD Ryzen 7 PRO 8840U、Radeon 780M、約 1 TB SSD、Windows 11 Pro；兩條記憶體回報 5600 MT/s。

當時可確認新增 RAM 已被辨識，後續取樣沒有記憶體不足跡象；兩次程式工作量不同，不能當成嚴格效能比較，也不能保證所有 SAP 卡頓都已解決。

原則：外接硬碟增加檔案空間，不會直接補充 RAM。需要保留 CPU、RAM、已認可記憶體、磁碟及特定程序的同時觀察，避免只看單一百分比。歷史商品報價未納入，因為與處理結果無關且不代表目前價格。

### VPN

### Obsidian

- 曾設定背景圖與全畫面 CSS；專案中有 fixed-full-background.css。
- 標題色：H1 #c792ea、H2 #ff72c6；專案中有 heading-colors.css，歷史回覆記錄已設定。
- QuickAdd 曾因 Insert after 目標為空而報錯；最後建議改放到檔案底部，待辦格式為 `- [ ] {{VALUE}}`。
- 「已提供設定步驟」不代表使用者已操作成功；QuickAdd 沒有最後確認結果。

## 8. 待辦與驗收

- [ ] 查 Agent 的啟動類型、復原及最近停止事件，保留時間線。

- [ ] 確認午夜排程的實際時區與 SQL 備份完成先後。
- [ ] 保存排程 0x0、END ExitCode=0、遠端檔案日期／大小。
- [ ] 定期還原一份備份並記錄結果。
- [ ] 補上失敗重試、不可重疊與備份未完成時不傳送的行為。
- [ ] 若 SAP 再卡住，記錄發生時間、操作、是否多人、程序與 SAP 日誌。
